# ZRust

https://github.com/pyrlyn/zrust

A Rust compiler written in Zig that emits machine code through LLVM. Track A reuses the rustc frontend and middle end through a thin Rust shim; the backend and the driver are Zig.

## How tasks map to the plan

Phases A0–A8 come from [`docs/AGENT_PROMPT.md`](../docs/AGENT_PROMPT.md) §9. One task per phase or sub-phase, one pull request per task. Phases not started yet are listed in [`roadmap.md`](../roadmap.md).

## Decisions

- **LLVM 22 comes from mise** (`conda:llvmdev`, pinned in `mise.toml`), on developer machines and in CI alike. `conda:llvm` alone ships only the shared library; the headers and `llvm-config` are in `conda:llvmdev`. `zig build -Dllvm-config=<path>` points the build at any other LLVM 22 install.
- **LLVM is linked dynamically** (`libLLVM-22`), with an rpath to the directory `llvm-config --libdir` reports.
- **No `@cImport`.** Zig 0.17.1 removed the builtin, so the LLVM-C bindings are generated by the build system (`b.addTranslateC` over `src/llvm/c.h`) and imported as the `llvm_c` module. This replaces the `src/llvm/c.zig` file named in `docs/AGENT_PROMPT.md` §7.
- **The shim is built by cargo into `shim/target/`**, then copied to `zig-out/lib/`. Cargo owns its own incremental state; the Zig build always re-invokes it.
- **rustc's own LLVM differs from ours** (the pinned nightly reports LLVM 23.1.6). The two never share a process: the shim spawns `zrust-codegen`.
- **ZRMIR is JSON in a canonical form** ([`docs/ZRMIR.md`](../docs/ZRMIR.md)): minified, fields in a fixed order. Decoding a file and encoding it again must give the same bytes, which is how `zrust-codegen --check` proves that the Rust and the Zig declarations of the format agree on every value that occurs. No test compares the two declarations themselves, so a tag no test program produces is only checked when it first shows up.
- **The shim needs `ZRUST_CODEGEN`.** It names `zrust-codegen`; the driver sets it, and without it a compilation is an error. `ZRUST_ZRMIR_ONLY=1` (`zrust dump-zrmir`) stops after writing and checking the ZRMIR, with a warning instead of a binary, so nobody mistakes a dump for a build. `ZRUST_KEEP_ZRMIR=1` only keeps the files of a build.
- **A ZRMIR module says how to compile itself.** Target, CPU, features, relocation model and optimization level are fields of the module, so `zrust-codegen` takes only `--in`, `--out` and `--emit`, not the `--target`, `--cpu` and `--opt` flags of `docs/AGENT_PROMPT.md` §5: a module and its flags cannot disagree.
- **The data layout of an LLVM module comes from LLVM's target machine**, not from the string rustc reports. rustc's string describes rustc's LLVM (23), ours is 22; sizes and alignments of values come from the ZRMIR layouts either way, and every `alloca`, `load` and `store` carries its alignment explicitly.
- **Refuse, never approximate.** A construct the code generator does not implement is an error that names the function, the block and the statement. A program is either compiled the way rustc means it or not compiled.
- **`default<O0>` runs too.** Every module goes through `LLVMVerifyModule` and the pass pipeline of its level, so the unoptimized path is the same code as the optimized one.
- **One `zrust-codegen` process per codegen unit, one after another.** Running them in parallel is A8.
- **No Zig file lives in a directory named `llvm`.** Zig's LLVM backend names a function after its file path, `llvm.emit.write`, and LLVM rejects a definition whose name starts with `llvm.` as an intrinsic. `src/llvm/` holds only `c.h`; the code that drives LLVM is in `src/codegen/`.
- **Run-pass tests state their expectations in header comments** (`expect-stdout`, `expect-exit`, `rustc-flags`, `unsupported`; see `README.md`). Stock rustc runs against the same header, and a program marked `unsupported` is checked to be refused, so the mark cannot outlive the gap it describes.
- **The shim crate is the large test input.** `zig build test` dumps `shim/src/lib.rs` (over 2000 lines, heavy use of generics, closures, traits and std) next to `tests/run-pass/`, each with and without `-O`. It is what found the LLVM-intrinsic calls version 1 of the format got wrong.
- **The driver runs rustc through `rustup run <pinned nightly>`**, reading the channel from `rust-toolchain.toml` at build time, so it works from any directory and ignores `RUSTUP_TOOLCHAIN`.
- **`zrust dump-zrmir` owns `target/zrmir/<file stem>/`**: it deletes stale `.zrmir` files there before a run, so the printed list is exactly what the run produced.
- **`zrust cargo` is postponed** until a crate can be built at all (A6 at the earliest).

## Known gaps after A3

What the code generator accepts today is compiled correctly but plainly. Missing, with the phase that needs it:

- Function attributes: `nounwind`, `uwtable`, frame pointers, `"target-cpu"` and `"target-features"` (the target machine's defaults apply), and the optimization attributes of arguments (`noundef`, `nonnull`, …). A4–A7.
- `dso_local`, `unnamed_addr` and the "PIC Level" / "PIE Level" module flags. A5.
- Calling conventions other than C and Rust; pass modes other than `ignore` and a `direct` scalar. A4–A5.
- `-C target-feature` is refused by the shim. A7.
- No allocator module, and `--emit=metadata`-only builds are not special-cased. A6.
- `zrust-codegen --emit=bc`.
- `rustfmt` is not part of the pinned toolchain, so the shim is formatted by hand.
